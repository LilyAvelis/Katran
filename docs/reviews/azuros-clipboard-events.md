# Azuros Claudapi: clipboard notifications, not a polling committee

Review of the current source, 2026-11-09. Verdict: Polly's central technical claim is correct. The existing implementation is a working, documented snapshot poller, but Windows offers a source-independent notification mechanism and Microsoft explicitly says not to use the sequence-number method in a polling loop for notification. This is an architectural improvement, not evidence of an urgent CPU incident. No product code was changed, no clipboard contents were read or written, and no GUI was operated.

## Findings

1. **P2 — Notification is available without source-specific polling.** The GUI schedules `PollClipboard` every 250 ms when eligible (`src/bin/ui.rs:28`, `:431–445`). The command compares `GetClipboardSequenceNumber` first and returns without opening the clipboard when it is unchanged (`src/capture.rs:6–19`). Thus it is not reading clipboard contents four times per second. Still, each eligible tick starts a fresh thread, transfers exclusive ownership of the service, executes the dispatcher and requests repaint on completion (`src/bin/api_client.rs:43–64`). When diagnostics are attached, the dispatcher enqueues a command and result record for each call (`src/lib.rs:130–145`); the logger serializes and queues those and a separate worker writes them (`src/diagnostics.rs:59–75`, `:87–107`, `:197–227`). The unchanged fast path performs no SQLite query or ingestion; successful captures alone trigger a UI refresh and its database queries (`src/bin/api_client.rs:97–104`, `:110–133`). Actual CPU, wakeups, I/O and energy attributable to this design have not been benchmarked.

   Microsoft says that a registered window receives `WM_CLIPBOARDUPDATE` on clipboard content changes, regardless of which application supplied them. This detects a change, not the identity, format or durable history of the content. Supported file/image retrieval still needs the existing adapter; applications providing inaccessible, delayed or unsupported formats do not thereby become supported. Microsoft describes the sequence number as useful for cache validation, says it **should not be used in a polling loop** for notifications, and recommends a format listener over the older viewer chain. It also documents delayed rendering and that the sequence number is not incremented until changes are rendered. Sources: [monitoring the clipboard](https://learn.microsoft.com/en-us/windows/win32/dataxchg/using-the-clipboard#monitor-the-clipboard-contents), [AddClipboardFormatListener](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-addclipboardformatlistener), [sequence number](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipboardsequencenumber).

2. **P2 — Capture scheduling depends on GUI presentation state.** No poll is started while Actions, save, shortcut editing, delete confirmation or Settings are open, a native drag is pending, or the service is occupied (`src/bin/ui.rs:431–445`). Repaint remains requested every 250 ms while capture is enabled even during these gates (`:390–392`). Multiple changes during a gate can collapse to the latest state. The scheduler lives in `render`, while `eframe::App::logic` only completes jobs and handles activation (`:448–478`). Therefore capture continuity when hidden, minimized or under native modal loops depends on actual eframe/Windows scheduling and is **not established by this review**. The owner should test it natively. This is a code-level coupling and test gap, not a claim that minimized capture has already failed.

3. **P2 — Preserve snapshot consistency and retry semantics during migration.** The adapter uses three immediate clipboard-open attempts per invocation; failure returns `clipboard_busy` without acknowledging the sequence, so later eligible polls retry. A changing sequence during the locked metadata snapshot returns `retry` (`src/capture.rs:17–25`, `src/origin.rs:69–90`). A file-list snapshot is taken under that lock; per-file ingestion results are returned and the sequence is acknowledged after the batch, including partial failures (`src/capture.rs:26–45`). An image is read after reopening, encoded, and its sequence rechecked before ingest and acknowledgement (`:47–81`). Unsupported format is acknowledged (`:83–85`); other image errors are returned without acknowledgement (`:87`). Retries across ticks are currently unbounded while the same change remains pending; three attempts per tick are not a bounded overall retry policy. Clipboard changes can overtake a retry, so neither polling nor notifications guarantee a complete history. `OpenClipboard` can fail while another window holds it, per [Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-openclipboard).

   Enable/disable snapshots the then-current sequence (`src/lib.rs:330–338`), so enabling skips the current clipboard; a service configured for capture at startup initializes its sequence to zero (`:91–100`), a distinct startup case. Successful Katran clipboard publication records its own receipt sequence (`:230–234`) to avoid immediately recapturing that publication. Preserve these distinctions explicitly, or document and test a deliberate change. Sequence checking suppresses rereading the same unchanged sequence; it does not promise content-based deduplication across separate copies.

## Passive observation, not a benchmark

One already-running `katran-ui` process was sampled with `Get-Process`, without launching, focusing or changing it: over 20.016 seconds its reported total process CPU increased by 0.000 seconds, or 0% of one logical core at the counter's reported resolution. The machine reported 32 logical processors. This was an uncontrolled live observation: capture state, user activity, window state and whether the running executable exactly matches this source were not established. It covers the whole process, not capture separately; it cannot establish the enabled-versus-paused difference, prove zero cost, or justify a performance claim.

## Migration proposal — API first

Write the capture contract and synthetic state-machine tests first. Introduce a thin native notification adapter registering a window with `AddClipboardFormatListener`; promptly coalesce notifications into a pending signal, leaving the dispatcher as the sole capture/ingestion authority. A dedicated message-only window on its own message-loop thread is a candidate that avoids subclassing eframe's window; verify registration, message delivery, teardown and integration on supported Windows. A thread creating a window needs a message loop ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/winmsg/using-messages-and-message-queues#creating-a-message-loop)). Registration errors and shutdown/unregistration must be explicit. Do not perform clipboard retrieval, encoding or SQLite work in the window procedure. Coordinate service ownership so delivery and retries do not rely on a rendered frame, and the GUI only receives completion/repaint signals. Do not introduce a second dispatcher or SQLite writer.

On notification, dispatch snapshot work with one in-flight operation, a dirty/coalesced flag and bounded, delayed retry on transient busy/unstable snapshots. Recheck the latest sequence after work and arrange another pass if an update arrived while busy; never acknowledge a newer change as the old snapshot. Define exhaustion and recovery explicitly, including later notifications and pause/re-enable, rather than silently dropping or spinning. Preserve per-item batch outcomes, origin association, own-copy suppression, current enable/startup semantics and deliberate unsupported-format acknowledgement. Keep `PollClipboard` as a compatible explicit API entry point if clients need it; the notification should trigger the same domain behavior, not a separate ingestion path. A notification is only a wake signal: Windows clipboard is a mutable current snapshot, not an event journal, so fast consecutive copies can still be lost or coalesced. Measure before claiming any improvement.

Native DnD already demonstrates why lifecycle and thread ownership must be designed, not guessed: the GUI invokes the prepared native operation on the window thread, with explicit cleanup after the modal loop (`src/bin/native_drag_ui.rs:1–22`). A clipboard listener has different requirements; this is evidence for careful integration, not a requirement to run clipboard reads on the UI thread.

## Verification before shipping

- Fake the native boundary and time: unchanged/duplicate signals, rapid changes, delayed rendering/sequence movement, lock contention then success and exhaustion, notification during in-flight capture, stale snapshot, unsupported formats, partial file failure, own-copy receipt, pause/resume and startup. Assert dispatch results, acknowledgement and no duplicate ingestion for the same acknowledged sequence; never use the owner's clipboard in automated tests.
- Owner's native Windows checks with synthetic material: Explorer files, browser image and unsupported text; repeat copies and fast successive copies; Settings/Actions, minimized/hidden windows, active DnD and busy clipboard; capture paused/resumed and restart with both startup settings; listener registration failure and clean shutdown where feasible. Confirm observations without promising lossless history.
- Conduct controlled enabled-versus-paused, unchanged-clipboard comparisons over multiple longer runs with the same build and window state. Measure whole-process CPU, wakeups/thread creation, diagnostics writes and memory, then isolate capture with tracing or instrumentation. Compare equivalent workloads before and after; document methodology, variability and limits.
