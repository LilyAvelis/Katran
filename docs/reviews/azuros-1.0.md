## Приоритетные находки

### P1. Экспорт hard link не является независимым снимком

`src/copy_out.rs:144` создаёт hard link из принадлежащего Katran blob в экспортируемый путь. Триггер: другая программа или пользователь открывает этот экспортируемый файл и записывает в него данные на месте. Изменяются те же физические данные, на которые ссылается исходный blob, и все события с ним; имя SHA-256 и SQLite размер остаются прежними. При следующем ingest исходных байтов проверка в `src/lib.rs:539` выявит расхождение, но уже сохранённый объект испорчен. Сценарий основан на семантике hard link и коде; взаимодействие с внешними приложениями не проверялось. Исправление: независимая копия либо настоящая copy-on-write копия с доказанными гарантиями; отдельно проверка целостности и тест, меняющий подготовленный экспорт при сохранности blob. Не разрушать ожидающий paste экспорт при удалении записи.

### P1. Аварийный `.tmp` блокирует повторную запись того же содержимого

`src/lib.rs:520`–`545`: имя staging детерминировано по хешу и открывается `create_new`. Синтетическое воспроизведение: после искусственной имитации сбоя в процессе записи оставить `blobs/<sha256>.tmp`, перезапустить сервис и передать соответствующие `ingest_bytes`. Получен `io_error`, Windows error 80 «файл существует»; последующий повтор не очищает staging. Аналогично после удаления файла blob до commit очистки `src/delete_shelf.rs:90` crash может оставить в БД строку blob без соответствующего файла: транзакция SQLite не возвращает файл; следующий ingest того же содержимого попытается прочитать отсутствующий файл. Это вывод по порядку операций, не инсценированный сбой ОС. Нужна согласованная стратегия восстановления, уникальные staging-файлы и повторяемая reconciliation при старте, с тестами сбоев в каждой фазе. Финальный orphan после rename не объявляется доказанным отказом повторного ingest: Windows rename может заменить целевой путь.

### P1. Экспорты вне квоты растут без установленного срока жизни

`src/copy_out.rs:97`–`145`; `src/lib.rs:247`; `docs/shelf-03.md`, раздел Copy. Каждый copy создаёт каталог, включая операции с одними внешними ссылками и неуспешные попытки; fallback делает отдельные полные копии, hard links удерживают данные после удаления последнего blob. Эти файлы не учитываются квотой. Это документированная граница, но при длительном применении пользователь может исчерпать место, считая что лимит защищает диск. Не чистить бездумно актуальные пути буфера: определить надёжный жизненный цикл, учёт размера, безопасную очистку с явной политикой и восстановление после сбоев; протестировать pending paste и ошибки копирования. Отнести в приоритет до широкого распространения, не к внезапному блокированию принятой версии.

### P2. Медленный старт: неоптимизированная сборка и последовательный полный decode

`scripts/build-working.ps1:5` собирает debug, устанавливается `target/build/debug/katran-ui.exe` (строка 7). `src/lib.rs:440`–`452` декодирует исходник целиком и лишь затем уменьшает; `src/bin/ui.rs:46`–`59` использует один worker, постоянного кэша миниатюр нет. Воспроизведение через тот же dispatcher CLI на синтетическом шумовом PNG 3000×2000, 15 254 404 байт, `max_edge=320`: четыре последовательных запроса debug 504,6 / 496,9 / 503,7 / 505,6 мс; release 46,8 / 47,3 / 47,2 / 47,0 мс (~10,7× по медианам). Это не замер холодного диска, фактического старта GUI, GPU, иных изображений или установленного exe; и debug, и release CLI собраны из доступных исходников. Измерение демонстрирует мощный и проверяемый рычаг, но не устанавливает единственную причину наблюдения пользователя. Сделать воспроизводимую оптимизированную сборку, отдельно измерить первый экран, затем рассмотреть постоянный versioned thumbnail cache, приоритет видимых и ограниченный параллелизм. Кэш для внешних ссылок инвалидировать по изменению файла, а для blob — по содержимому.

### P2. Повторное использование ID показывает старую миниатюру другого объекта

`src/lib.rs:179` использует `INTEGER PRIMARY KEY` без гарантии неповторности удалённого последнего ID. Синтетический API-тест: ingest id=1, delete, ingest иных bytes → вновь id=1. `src/bin/ui.rs:36` и `:65`–`:120` ключуют текстуру по `(id, edge)` и после удаления её не инвалидируют. При том же процессе и прежнем загруженном превью новый объект может получить старую картинку; это особенно опасно при выборе объекта для отправки или удаления. Повторное ID измерено; последствия для UI выведены из кода, не проверялись в окне. Нужны невозвращаемые идентификаторы/ревизия содержимого и инвалидация существующих и отложенных запросов после изменения. Покрыть headless/API тестом реальное совпадение ID и ожидание правильной текстуры.

### P2. Очередь превью не приоритизирует актуальный экран; кэш сбрасывается целиком

`src/bin/ui.rs:43`–`:60`, `:84`–`:105`, `:625`: viewport виртуализирован — это хороший выбор, но все уже запрошенные элементы остаются в неограниченной FIFO и выполняются единственным worker; быстрая прокрутка оставляет новые видимые изображения за устаревшими. При 96 текстурах или 48 МиБ очищается весь кэш и `requested`, а старые заявки могут ещё исполняться, создавая повторы. Ошибочный preview запоминается как `None` до общего сброса, даже если внешний файл снова появился. Риск/масштаб выведены по коду; конкретные задержки прокрутки не измерялись. Использовать ограниченную очередь с поколениями, отменой/дедупликацией и приоритетом видимых, LRU и явным retry; проверять ограничение памяти при скролле и открытии больших preview.

### P2. Поиск и полка ограничены последними 1000 записями

`src/lib.rs:331`–`:356`, `:469`–`:483`; `src/bin/ui.rs:160`: Search сначала запрашивает последние `limit`, затем фильтрует в памяти. Следовательно совпадение старше последних 1000 не найдётся даже при точном имени, а GUI не предоставляет следующую страницу. Это детерминированное следствие кода, не нагрузочный замер. List выполняет отдельный `get` и filesystem `is_file` на каждый объект, плюс UI клонирует и пересылает весь список при кадре (`src/bin/ui.rs:539`), что следует измерить на медленных/сетевых путях. Нужны фильтрация до LIMIT и стабильная пагинация; сохраните ясный контракт области поиска.

### P2. Захват и copy могут блокировать поток интерфейса; частичные ошибки захвата скрыты

`src/bin/ui.rs:433` вызывает PollClipboard синхронно в кадре; `src/lib.rs:637`–`:669` читает bitmap, кодирует PNG и пишет/синхронизирует blob в том же вызове. `src/bin/ui.rs:171` запускает copy синхронно, где `src/copy_out.rs:190` декодирует полноразмерное изображение до публикации. Большие изображения и медленный диск способны заморозить интерфейс; долгота не измерялась, нативный clipboard не затрагивался. Для списка файлов API возвращает `items` с отдельными ошибками (`src/lib.rs:608`–`:631`), но UI лишь проверяет число удачных (`src/bin/ui.rs:22`, `:433`), не показывает ошибки отдельных файлов. Перенести тяжёлую работу в ограниченный worker, сохраняя dispatcher как источник поведения и корректную семантику последовательности; показывать частичные неудачи и повторную попытку. Оговорка: запланированные события быстрее 250 мс могут пропасть, что уже честно документировано.

### P3. Cleanup и предупреждения недостаточно видимы

`src/delete_shelf.rs:59`–`:104` честно возвращает `cleanup_pending` после успешного удаления, но `src/bin/ui.rs:181` и `:732` показывает только количество удалённых. При недоступном файле/quota учёт и фактическое место могут расходиться без понятного сигнала; UI сохранения отображает лишь число успешных результатов (`:764`), не причины по каждому объекту. Показать пользователю ошибки и предложить безопасный повтор обслуживания. Это не основание отрицать лично подтверждённое массовое удаление.

## Проверки и ограничения

- `cargo test --offline --features ui`: 24 теста прошли (4 library, 5 headless UI, 15 integration); doc tests 0. `cargo clippy --offline --all-targets --features ui -- -D warnings`: успешно. Штатный тест переключения capture вызывает Windows GetClipboardSequenceNumber: это чтение системного номера последовательности, не содержимого буфера и не изменение буфера. Desktop automation не использовалась. Тесты не доказывают paste, внешний вид, сбои питания или производительность в GUI.
- Синтетические скрипты и данные: `target/review_bench.py`, `target/review_id.py`, `target/review-fixture/`. Выполнены штатным `target/debug/katran.exe` и отдельно собранным `target/release/katran.exe`. Шумовой PNG сгенерирован Pillow; для benchmark один процесс, один path-reference event, четыре последовательных PreviewImage, замер wall-clock вокруг JSON request/response с разбором результата. Это сочетает API, decode, resize и base64/JSON; ОС могла кэшировать файл. Полный GUI и реальный профиль нагрузки не измерялись.
- Изучены source/tests/build/docs. Не читались личные файлы `katran-data/exports`, не менялись исходники и пользовательские данные, GUI не запускался; содержимое системного буфера не читалось и не изменялось. Тесты и сборка пишут только в `target` и временные синтетические каталоги.
- Дизайн API First в целом виден: команды сосредоточены в Service, интерфейс вызывает dispatcher; Afio не является runtime dependency. Пер-предметные ошибки импорта/копирования и подтверждение exact-ID заложены. Сервис и preview worker открывают отдельные подключения, а документация ограничивает один writer: конкурентный многопроцессный контракт и protected IPC пока не реализованы. Проблемы с clipboard sequence/реальными приложениями за пределами разрешённого испытания не объявляются воспроизведёнными.
