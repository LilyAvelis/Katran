# Azuros Claudapi: модульность Katran для совместной работы агентов

Дата: 2026-11-09. Это независимая оценка организации исходников и документации, не план нового продукта и не разрешение на рефакторинг. Смотрел код и тесты без запуска GUI, чтения буфера обмена или пользовательских данных. Ранее выполненные тесты и ограничения описаны в `azuros-1.0.md`; новых тестов для этого обзора не запускал. Родитель параллельно обновляет скрипт сборки и документацию расширения; оценка ниже относится к прочитанному состоянию и предлагает проверить эти изменения после их завершения.

Ach, командный центр в двух файлах! Слабому агенту опасно давать десять почти одинаковых поручений, когда каждое затрагивает один и тот же `match`. Но Nein: строить фреймворк плагинов или разносить проект на десятки крейтов сейчас не нужно. Задача — сделать маршрут изменений очевидным, а места конфликтов немногочисленными и честно обозначенными.

## Приговор и находки

**P1 для многoагентной разработки: общий узел регистрации и поведения.** В `src/lib.rs:32` определяется `Command`, `:251`–`:589` содержит диспетчер и одновременно многие реализации. Добавление возможностей разными агентами приводит к частым изменениям в одном месте; в частности две независимые ветви действия затрагивают общий `RunAction`. Это риск конфликтов и пропуска связи, а не доказанная текущая ошибка исполнения. При этом единый enum и исчерпывающий `match` полезны: компилятор видит недостающую обработку. Оставить один настоящий dispatcher и статические типы, но вынести семейства операций в обычные Rust-модули.

**P1 для расширений: одна команда регистрируется вручную в нескольких местах.** Метаданные Actions находятся в `src/lib.rs:385`, выполнение в `src/lib.rs:403`, shortcut и его политика в `src/shortcuts.rs:32`, отображение значка в `src/bin/action_icons.rs:3`, а отдельные намерения — в `src/bin/ui.rs:169`. Так, `commands` есть в shortcuts, но намеренно не показан в палитре; надпись capture меняется по состоянию. Агент, не знающий исключений, может добавить команду, видимую только в одной части интерфейса. Вывести ID, базовую подпись, группу, включение в палитру и стандартное сочетание/права редактирования в одну статическую таблицу; динамический текст оставлять функцией от состояния, а иконку — в GUI с безопасным fallback. Маршрутизацию сохранить через типизированный enum или явный исчерпывающий match. Тестировать согласованность реальных catalogue/shortcuts/RunAction, не требуя, чтобы скрытый `commands` появился в палитре.

**P2: `src/bin/ui.rs` объединяет слишком много разных зон.** `Images` (`:36`), вызовы и интерпретация результатов (`:147`), Actions (`:217`), ввод/опрос/перетаскивание (`:403`), список и навигация (`:528`), модальные операции (`:724`) и headless tests (`:834`) живут вместе. Агент, меняющий цвета карточки, сталкивается с агентом, меняющим клавиатуру и worker. Уже существуют полезные отдельные `settings_ui`, `shortcuts_ui` и `ui_style`; продолжить тем же способом. Разделение само по себе не исправляет очередь или скорость и не означает переход бизнес-правил в компоненты.

**P2: включение настройки требует безопасной эволюции данных.** `src/settings.rs:5` использует строгую десериализацию всей структуры без defaults, `Service::open` читает документ в `src/lib.rs:197`–`:210`. Если просто добавить обязательное поле, существующий JSON без него перестанет загружаться, приложение не откроется. Миграция/default, проверка старого документа, повторный запуск и валидация должны быть частью маршрута каждой новой настройки. Нельзя молча подменять испорченные пользовательские настройки значениями по умолчанию. Это вывод по коду; чужая база не открывалась.

**P2: новая точка входа для агента пока не обозначена однозначно.** `AGENTS.md` ясно задаёт API First и запрет управления рабочим столом; `README.md` — текущий запуск; `docs/shelf-03.md` — договорённости, но истории `docs/shelf-02.md` всё ещё содержат устаревшую прямую команду запуска. Из-за этого агент может принять исторический путь за актуальный. Пометить старые документы историческими в первой строке со ссылкой на README; один короткий index/guide со ссылками лучше дублирования команд и спецификаций. Родитель уже готовит extension docs: эта рекомендация не предполагает, что их ещё нет к моменту выполнения.

## План маленьких изменений: один интегратор на общую границу

1. **Первым — маршрут и страховочные тесты, без перестройки.** В README добавить ссылку на один `docs/development.md` или уже создаваемый родителем эквивалент; в нём карта файлов, матрица ниже, правила API First, синтетические тесты и проверка изменения существующих данных. Отдельным тестом контрактов проверить уникальность ID и ожидаемую согласованность каталога, shortcuts и маршрутизатора, включая скрытые/защищённые команды, недопустимый ID и динамический label. Не выполнять каждое действие вслепую: copy и capture обладают внешними эффектами; применять явные synthetic fakes/безопасные действия. Владелец — интегратор API/контрактов. Это страховка перед переносами.

2. **Вынести описания API без изменения wire format.** Например `src/api.rs`: `Request`, `Command`, `ApiError`, `Event` и константы; в `src/lib.rs` оставить `pub use` с прежними публичными путями. Запретить случайное переименование `serde` тегов/полей, изменений структуры ответа и поведения неизвестных полей. Сохранить `Service::execute` единственной точкой прохождения команды; `tests/stdio.rs` и существующие API tests — контроль. Владелец — один интегратор; новые фичи в общий enum на время этого переноса не сливать.

3. **Вынести реализацию по владению данными, оставив явный match.** Например: `src/storage.rs` владеет открытием SQLite, схемой, запросами и жизненным циклом blob; `src/preview.rs` владеет вычислением PreviewImage; `src/capture.rs` — Windows snapshot-адаптером и преобразованием в команды ingest; `src/actions.rs` — каталог и маршрутизация действий. Это ориентиры, а не обязательное дробление в одном коммите. Начать с одной функции или семейства за перенос, сохраняя границу транзакций/ошибки и проверяя API до/после. Не выдавать UI прямой доступ к storage и не создавать второго `Service`. Существующие `delete_shelf.rs`, `copy_out.rs`, `origin.rs`, `settings.rs`, `interaction.rs`, `shortcuts.rs` — уже рабочие границы; не разбивать их без конкретной причины. Перенос capture не должен незаметно менять последовательность чтения clipboard. Структурный перенос и отдельные исправления целостности из первого аудита — разные изменения.

4. **Свести описание action к одному набору данных.** В `src/actions.rs` держать статические записи (`id`, базовый label, group, `in_palette`, default binding, rebindable); `Actions` и `Shortcuts` строить из них. Таблица не должна сама хранить состояние UI, closures, callback framework или создавать отдельный путь операции. `RunAction` по-прежнему вызывает dispatcher/существующие доменные функции; `commands` остаётся скрытым из палитры, `settings` защищённым, capture label динамическим. По мере необходимости использовать небольшой `enum ActionId` с явным преобразованием строк и обработкой unknown ID. Владелец — интегратор API; shortcut-агент и UI-агент согласуют один формат, а не редактируют три реестра параллельно.

5. **Разнести GUI по ответственности с узкими входами.** Сначала перенести worker/texture state в `src/bin/images.rs`, затем палитру в `src/bin/palette.rs`, затем рендер списка/превью в `src/bin/shelf_view.rs`; тонкий `ui.rs` связывает `Shelf`, команды и ввод. Названия примерные; не нужны десятки однострочных модулей. Модули получают состояние отображения и доступ к вызову `Command`; они не меняют файлы, SQLite и политику selection напрямую. Сначала сохранить порядок событий и headless tests, отдельно заниматься производительностью. Прямой helper `Service::execute` в UI, как сейчас, допустим; новый transport/trait нужен лишь когда он реально улучшает синтетическое тестирование или подмену опасного адаптера.

6. **Закрепить совместимость и документировать границы.** Минимум: старый JSON настроек без добавленного поля открывается и получает документированный default, неизвестные/повреждённые данные не обнуляются молча; действующие stdio JSON-примеры и error/partial-failure контракт сохранены; одноместный writer, отсутствие live IPC и ответственность owner за Windows UI остаются явными. При невозможности совместимости — явная миграция и тест до слияния, а не случайное повышение версии API.

## Четыре маршрута для исполнителя

Ниже — ожидаемая минимальная последовательность. После извлечений названия модулей могут отличаться; публичная команда и правила остаются опорой. Точки, где сегодня всё ещё обязателен общий файл, названы прямо.

| Задача | Сначала API и данные | Затем клиент | Проверить синтетически |
|---|---|---|---|
| Новое действие | Поведение как `Command` и обработка через `Service::execute`; action ID/описание, shortcut и `RunAction`: сейчас `src/lib.rs` + `src/shortcuts.rs`, после шага 4 — `actions.rs`. Для UI-only намерения явно вернуть intent. | Отобразить intent/иконку в GUI только если нужно; `action_icons.rs` может использовать fallback. | Доступность по API, результат/ошибка, выборка, catalogue/shortcut consistency, конфликты, protected chords, сохранение при перезапуске; native clipboard не вызывать. |
| Новый источник | Адаптер получает внешнее событие и вызывает существующие `IngestPath`/`IngestBytes` или новую доменную команду через Service; `origin.rs` для проверяемого происхождения. Семантика ссылок/копий, ошибок и повторов определена в API до GUI. | Добавить управление или индикатор после результата API; адаптер не обходит доменное хранилище. | Synthetic input, unsupported/missing/частичные ошибки, пауза/retry и отсутствие изменения source; без реального clipboard. |
| Новый вид | `interaction::View` и состояние/команды selection в `src/interaction.rs` и dispatcher; если сохраняется значение по умолчанию — совместимая схема settings. | Отрисовка `shelf_view`, перевод геометрии навигации в параметры вызова API; не менять правила выбора в карточках. | Переключение/selection/navigation и старые виды через API; headless тест адаптера только для ввода; визуальную Windows-проверку делает владелица. |
| Новая настройка | `src/settings.rs`: тип, безопасное значение для старого JSON, validation; `SetSettings`/применение в Service и ожидаемая семантика после restart. Проверить границы и миграцию. | Контрол в `settings_ui.rs`, получает и отправляет настройки командами, показывает ошибку. | Старый документ без поля, новый документ, неверное значение без изменения сохранённых данных, restart, единицы измерения и поведение API. |

Это не обещание, что добавление полностью новой domain-команды вообще обойдётся без правки центрального enum: явная регистрация в одном месте полезна. Цель — один маленький заранее оговорённый общий файл, а не сложная магия автоматической регистрации.

## Совместная работа без случайных конфликтов

- Интегратор владеет `Command`/wire format, общей регистрацией и схемой SQLite. Каждой параллельной задаче заранее задаются вход, результат, семантика ошибок и список своих файлов; точки общего enum/catalogue интегратор объединяет последовательно. Владение здесь — соглашение команды, не ограничение ОС.
- Пример одновременно: агент A — `preview.rs` и `tests/preview.rs`; B — `settings.rs`, `settings_ui.rs`, `tests/settings.rs` после согласования схемы; C — `palette.rs` и headless tests на существующих контрактах; интегратор — `api.rs`, `actions.rs`, общий dispatcher. Если агентам нужен один файл или конфликтующие типы, перенести одну интеграцию в конец, а не менять общую ветвь вслепую.
- Каждый агент сначала читает `AGENTS.md`, текущий README, одну карту модулей и договор нужного API; затем соответствующий тест. Не копировать исторические build commands и не делать GUI-first прототип. Запускать тестируемую синтетическую фикстуру до GUI и вновь после интеграции. Для новых тестов избегать любых вызовов реального clipboard, включая метаданные последовательности; текущий штатный тест SetCaptureEnabled вызывает `GetClipboardSequenceNumber`, что отмечено в первом аудите.
- У общего репозитория и общего `target` параллельные сборки могут ждать lock, а совместная запись в одни файлы — затереть работу. Раздельные worktree/ветки полезны при реальной параллельной работе, если они доступны и разрешены; слияние проводит один интегратор. Не делать параллельных модификаций одной SQLite-базы или пользовательских файлов ради тестов.
- На приёмке каждой порции: форматирование затронутого кода, целевые synthetic API tests, затем объединённые `cargo test --offline --features ui` и `cargo clippy --offline --all-targets --features ui -- -D warnings` по установленному контракту проекта; существующий вызов метаданных clipboard в одном штатном тесте следует учитывать. Сборку для ручной визуальной проверки готовить по актуальному README; агент не открывает окно. Не объявлять ручную проверку выполненной без владельца.

## Чего не строить заранее

Не вводить plugin SDK, сервисную шину, dependency-injection контейнер, async runtime или отдельный crate на каждую строку меню только ради числа агентов. Не переносить выбор/удаление/импорт в виджеты и не делать вторую базу для клиента. Сначала договоры, выделение ответственности и воспроизводимый тест; новая абстракция оправдана, когда удаляет реальное дублирование или делает опасный адаптер проверяемым.
