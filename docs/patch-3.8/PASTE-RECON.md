# Paste to previous window: read-only reconnaissance

2026-11-17. Source read began at local HEAD `5acd8e1`; global-hotkey changes were underway concurrently, so the capture/activation call sites must be rechecked against the final integrated commit before implementing a fix. This is a code and existing-test review, not a native reproduction. No window, Clipboard, user file, recipient, network or desktop was manipulated; no new tests or build were run.

Lilia reports two independent symptoms: (1) when Katran is already open and she focuses another window then returns to Katran, Enter can target an older window until resummon; (2) entering a file in Telegram usually works, while Notion/chats can fail in situations where Raycast works. Both are user observations, not independently confirmed here. The second report does not identify file type, clipboard formats, exact recipient context or whether focus, publication or recipient acceptance was responsible.

## Call map and actual success boundary

1. Enter is normally the rebindable `paste_previous` action (`src/shortcuts.rs`, `src/actions.rs`, `src/bin/shortcuts_ui.rs`); focused text controls and other modal contexts retain their own input. `src/bin/api_client.rs` routes that intent to `Shelf::paste_previous` in `src/bin/overlay_ui.rs`. The latter dispatches `BeginPastePrevious` and polls `CompletePastePrevious`; it hides Katran on `state = sent`.
2. `src/overlay_service.rs::begin_paste_previous` validates the saved previous target and queues `CopySelectedObjects`. `src/jobs_service.rs` snapshots the selected `SelectionRef {id, revision}` values (cursor if no selection) and routes `CopySmart`: all tables to table clipboard, all links to Unicode text, all text/Pods to Unicode text (Pods use no separator; other text uses blank-line separation), otherwise checked file export. Check mixed selections separately; do not assume they retain each item's preferred format.
3. `complete_paste_previous` requires a successful copy, no per-item failures and a nonzero publication sequence. A failed/partial copy prevents input. Some optional format warnings do not count as per-item failure: a file-list publication can succeed while image pixels failed. Clipboard publication is not recipient acceptance.
4. `src/overlay.rs::Session::paste` verifies the stored HWND, PID and process-creation time, waits for modifiers to be released, activates the target top-level window, rechecks foreground/identity and requires a clipboard sequence. `src/overlay_windows.rs::WindowsHost::send_paste` checks sequence and foreground/identity again, then injects Ctrl-down, V-down, V-up, Ctrl-up with `SendInput`. A short input send reports an error and performs best-effort key release without re-sending. Successful injection consumes the saved session. Windows may deny foreground activation or block input across integrity levels/UIPI. An unavoidable race remains between final checks and input.
5. A `sent` receipt means Windows accepted all four input events; there is no acknowledgement that the recipient read the clipboard, had a focused editable control, accepted its formats or attached a file. A successful `SetForegroundWindow` is a top-level foreground check, not proof of the currently focused child/control, document, tab, web editor or recipient-side upload.

## Target selection: supported explanation for symptom 1

`src/overlay.rs::Session` retains a single `previous` identity. It is assigned only by `summon`/`adopt`; a captured target is revalidated against own process, HWND/PID/process creation time and foreground. `src/overlay_windows.rs` captures the foreground on the global summon thread before Katran is shown; the UI adopts that receipt through `ToggleResidentOverlay` / `summon_captured_overlay`. Repeated self-summon preserves rather than replaces the target. `Session::paste` clears the target after successful input; failed validation/delivery leaves it available for retry.

At the reviewed state, tray `Show`/`Toggle` invokes `apply_window_visibility` without acquiring a new external target. A single-instance/Raycast relaunch signals the running instance; `ui.rs` calls `ActivateWindow`, `SetWindowVisibility` and `single_instance::show` without passing a prior external HWND. A manual click to refocus an already-open Katran has no corresponding external-target adoption path in the reviewed code. Thus an older valid target retained from an earlier summon can remain authoritative; a missing/cleared target instead reports `no_previous_target`. This is a concrete mechanism consistent with the first report, not proof of the exact native event sequence that occurred. A click after foreground has already become Katran cannot recover the old external window from `GetForegroundWindow` alone.

Before choosing a fix, review the final global-shortcut diff and distinguish: first launch, captured summon, single-instance relaunch, tray, focus B → click Katran, same-process windows, no external target, successful paste then repeat, and target change while a copy is pending. A foreground-event observation strategy is one option to evaluate, not an implementation directive: it would need bounded lifecycle/teardown, process and window identity, filtering own/transient shell windows, no titles/content/path logging, no stale or spoofed captures, correct thread/virtual-desktop behavior, and explicit rules for event order/activation races. Preserve last-target security revalidation and make ambiguity an explicit error rather than guessing a destination. Do not blindly overwrite a verified queued paste target or trust UI-supplied HWND.

## Published formats and limitations

| Selection | Current native publication | Important limitation |
| --- | --- | --- |
| Text, links, saved/virtual Pods | `CF_UNICODETEXT` and ownership marker through `src/text_clipboard.rs`; text is produced by existing smart-copy policy. | Text is not an attached file; virtual emoji Enter uses ordinary text copy, unlike catalogue Ctrl+C import semantics. |
| Tables | Unicode TSV text and registered `HTML Format`, with marker (`table_clipboard.rs`, `table_service.rs`). | Publication can be partial after clearing clipboard; `table_copied` is true only when both primary formats succeed. Recipient decides how to interpret them. |
| Single file/image | Prepared independent export path as `CF_HDROP` (15), copy `Preferred DropEffect` when available. If single file decodes as an image within limits, Katran also attempts `CF_DIBV5` (17); orientation and alpha are included. | Pixel conversion has a 32-million-pixel/256 MiB budget and can fail. CF_HDROP remains primary; a DIB failure is a warning. No code here establishes that recipient will choose attachment vs pixels. |
| Multiple files or mixed non-text selection | `CF_HDROP` references exported files; no multi-image DIB payload. Per-item copy failures are reported. | No assumption that a browser editor, chat, desktop app or website consumes HDROP. No evidence of a virtual-file `FileGroupDescriptor`/`FileContents` clipboard publication in this path. |

The clipboard file paths refer to Katran-managed export copies, not the original; the next successful publication may clean older export directories (`src/copy_out.rs`). Deferred recipient reads, clipboard replacement and path lifetime therefore deserve controlled investigation, but current code alone does not establish that they explain the reported failure. The separate native drag path (`src/drag_out.rs`) constructs a Shell `IDataObject` and invokes `DoDragDrop`; its behavior cannot be used as proof of clipboard paste interoperability. Do not assume Raycast's formats or delivery mechanism without a controlled comparison.

`WindowsHost::send_paste` normally requires the recorded sequence to match; for text only, `verified_text_paste_sequence` may accept a narrowly verified persisted owned-text state after rechecking marker/formats/bounded text (`src/text_clipboard.rs`). This must not be generalized to files or arbitrary changed clipboard content. Sequence checks prevent an unrelated clipboard change from being pasted, but don't prove which format a receiver consumed.

## Existing synthetic evidence and specific gaps

* `tests/overlay.rs` injects Host and checks target identity replacement, focus loss, modifier hold, activation failure, clipboard replacement, self-target, adoption after owner activation and single-use send. `tests/overlay_api.rs` checks copy-before-paste, explicit copy failure and one-shot dispatch using a fake text clipboard/Host. These tests do not use real Windows foreground, clipboard or receiver controls.
* `tests/window_activation.rs` checks the dispatcher activation serial; it does not assert that normal activation captures an external window. `src/bin/ui.rs` refocus tests cover keyboard/widget focus, not the previous external paste destination. Missing: A captured → external B foreground → click/activate Katran → Enter; activation via single-instance/tray/hotkey; A invalidated/closed/reused PID; shell/transient focus; same PID different top-level; arrival during pending copy; success clears target and next invocation; ordered event races.
* `src/copy_out.rs` tests synthetic group file-list encoding and a single-image DIB buffer; `tests/file_visual.rs`, clipboard/text/table and drag tests cover their own boundaries. These do not establish end-to-end native clipboard format negotiation or recipient acceptance. Add injectable publication/consumer tests for format order, optional DIB failure/warning, HDROP contents and paths, single vs multi selection, Unicode/link/table/mixed cases, partial failures, sequence change, delayed read and export lifecycle. Confirm formats through controlled synthetic native fixture, without touching personal Clipboard, then let Lilia perform real app checks if she chooses.
* `tests/external_paste.rs` is the opposite direction—external clipboard files copied **into** Folder—and should not be cited as evidence of Enter pasting out to a previous app. `tests/drag_lifecycle.rs` checks native-drag preparation with an injected runner, not Ctrl+V delivery.
* Diagnostics currently record `paste_delivery` success/error code and clipboard sequence, plus overlay show/hide events. This does not identify selection kind, offered formats, warnings, target focus control, target acceptance or upload. Consider opt-in, bounded, privacy-preserving diagnostics (stage, format flags, counts, timing, error categories; no paths, URLs, window titles or content), while respecting existing user settings. Avoid changing safety boundaries to improve telemetry.

Suggested owner-operated comparison when a candidate exists: on synthetic files and a fresh test destination, first compare Katran Ctrl+C then manual Ctrl+V, Katran Enter, and Raycast with the same file and focused editor; separate a single PNG, a non-image file and multiple files; record app/native vs browser and whether attachment or pixels were expected. Repeat with A → B → Katran targeting and capture of any explicit error. No sending or publishing is required. Results distinguish publication, focus and recipient-specific behavior without asserting any vendor compatibility in advance.
